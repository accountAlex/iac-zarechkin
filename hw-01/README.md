# Домашняя работа №1

## Развёртывание стенда средствами командной строки провайдера

**Вариант:** 11  
**Префикс ресурсов:** `zarechkin-11`

Репозиторий содержит сценарии для автоматического создания, проверки и удаления демонстрационного стенда в Yandex Cloud.

---

## Состав стенда

В состав инфраструктуры входят:

- виртуальная сеть `zarechkin-11-net`;
- подсеть `zarechkin-11-subnet-a` в зоне `ru-central1-b`;
- подсеть `zarechkin-11-subnet-b` в зоне `ru-central1-d`;
- два веб-сервера:
  - `zarechkin-11-web-1`;
  - `zarechkin-11-web-2`;
- сервер приложения `zarechkin-11-app` без публичного IP-адреса;
- NAT Gateway `zarechkin-11-nat`;
- таблица маршрутизации `zarechkin-11-rt`;
- целевая группа `zarechkin-11-tg`;
- Network Load Balancer `zarechkin-11-lb`.

Веб-сервис работает на порту `8033`.

Первоначальная настройка виртуальных машин выполняется с помощью `cloud-init`.

---

## Файлы

В каталоге `hw-01` находятся:

- `create.sh` — создаёт стенд;
- `check.sh` — проверяет состояние стенда;
- `destroy.sh` — удаляет созданные ресурсы;
- `cloud-init.tpl.yaml` — шаблон `cloud-init`;
- `README.md` — описание порядка работы.

Сгенерированный файл `cloud-init.yaml` содержит подставленный открытый SSH-ключ и поэтому не хранится в Git.

---

## Требования

Перед запуском необходимо установить и настроить:

- Yandex Cloud CLI `yc`;
- `jq`;
- `envsubst`;
- SSH-клиент.

Также должен существовать открытый SSH-ключ:

```bash
~/.ssh/id_ed25519.pub
```

Yandex Cloud CLI должен быть предварительно настроен на нужный каталог и облако.

---

## Создание стенда

Для создания инфраструктуры с параметрами варианта выполните:

```bash
./hw-01/create.sh
```

Сценарий последовательно создаёт:

1. виртуальную сеть;
2. две подсети;
3. NAT Gateway;
4. таблицу маршрутизации;
5. два веб-сервера;
6. сервер приложения;
7. целевую группу;
8. Network Load Balancer.

После создания сценарий ожидает перехода обоих веб-серверов в состояние `HEALTHY`.

При успешном завершении выводится публичный IP-адрес балансировщика.

---

## Идемпотентность

Сценарий `create.sh` является идемпотентным.

Перед созданием каждого ресурса выполняется проверка его существования. Если ресурс уже существует, его повторное создание пропускается.

Повторный запуск:

```bash
./hw-01/create.sh
```

не создаёт дубликаты ресурсов и не завершается ошибкой из-за уже существующей инфраструктуры.

---

## Параметры `create.sh`

Поддерживается следующий приоритет значений:

```text
аргумент командной строки
→ переменная окружения
→ значение по умолчанию
```

Поддерживаемые аргументы:

```text
--prefix
--web-count
--app-port
--greeting
--env
```

Пример запуска:

```bash
./hw-01/create.sh \
  --web-count 2 \
  --app-port 8033 \
  --greeting devlab
```

Параметры также можно задавать через переменные окружения:

```bash
WEB_COUNT=2 APP_PORT=8033 ./hw-01/create.sh
```

Если одновременно указаны переменная окружения и аргумент командной строки, используется значение аргумента командной строки.

## Проверка стенда

Для проверки состояния инфраструктуры выполните:

```bash
./hw-01/check.sh
```

После этого можно вывести код завершения:

```bash
echo "exit code: $?"
```

Сценарий выполняет три проверки:

1. Network Load Balancer отвечает HTTP-кодом `200`;
2. ответы поступают более чем от одного веб-сервера;
3. сервер приложения доступен с веб-сервера по внутреннему IP-адресу.

Если все проверки выполнены успешно:

```text
exit code: 0
```

Если хотя бы одна проверка не пройдена:

```text
exit code: 1
```

Пример штатного результата:

```text
==> проверка стенда
✓ балансировщик отвечает: HTTP 200
✓ ответили машины: zarechkin-11-web-1 zarechkin-11-web-2
✓ сервер приложения доступен с web-1
✓ стенд исправен
```

## Проверка отказоустойчивости

Для проверки отказоустойчивости можно остановить `nginx` на одном из веб-серверов.

Например:

```bash
ssh student@<PUBLIC_IP_WEB_1> "sudo systemctl stop nginx"
```

После этого необходимо запустить:

```bash
./hw-01/check.sh
echo "exit code: $?"
```

Балансировщик должен продолжать обслуживать запросы через второй веб-сервер, однако `check.sh` должен вернуть код `1`, так как стенд находится в деградированном состоянии.

Для восстановления веб-сервера:

```bash
ssh student@<PUBLIC_IP_WEB_1> "sudo systemctl start nginx"
```

После восстановления повторный запуск `check.sh` должен завершиться с кодом `0`.

---

## Сервер приложения

Сервер:

```text
zarechkin-11-app
```

не имеет публичного IP-адреса.

Он доступен только по внутреннему адресу из виртуальной сети.

Исходящий доступ в интернет осуществляется через NAT Gateway и таблицу маршрутизации. Это позволяет серверу устанавливать необходимые пакеты при выполнении `cloud-init`, не открывая прямой входящий доступ из интернета.

---

## Удаление стенда

Для полного удаления инфраструктуры выполните:

```bash
./hw-01/destroy.sh
```

Ресурсы удаляются с учётом зависимостей в следующем порядке:

1. Network Load Balancer;
2. целевая группа;
3. виртуальные машины;
4. отвязка таблицы маршрутизации от подсети;
5. таблица маршрутизации;
6. NAT Gateway;
7. подсети;
8. виртуальная сеть.

Сценарий допускает повторный запуск и пропускает уже отсутствующие ресурсы.

---

## Проверка после удаления

После выполнения `destroy.sh` можно проверить отсутствие пользовательских ресурсов:

```bash
yc compute instance list
yc compute disk list
yc load-balancer network-load-balancer list
yc load-balancer target-group list
yc vpc subnet list
yc vpc route-table list
yc vpc gateway list
yc vpc network list
```

После удаления стенда команда:

```bash
./hw-01/check.sh
echo "exit code: $?"
```

должна вернуть:

```text
exit code: 1
```

так как балансировщик больше не существует.

---

## Действия при ошибке `check.sh`

Если `check.sh` возвращает код `1`, необходимо проверить состояние виртуальных машин:

```bash
yc compute instance list
```

Проверить состояние backend-узлов балансировщика:

```bash
yc load-balancer network-load-balancer target-states \
  --name zarechkin-11-lb \
  --target-group-id $(yc load-balancer target-group get \
    --name zarechkin-11-tg \
    --format json | jq -r '.id')
```

Также необходимо проверить:

- состояние `nginx` на веб-серверах;
- доступность балансировщика;
- доступность сервера приложения по внутреннему IP-адресу;
- наличие необходимых облачных ресурсов.

После устранения проблемы необходимо повторно выполнить:

```bash
./hw-01/check.sh
```
